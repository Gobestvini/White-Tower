## 4. Требуемое поведение

- Сравнить два разумных варианта лёгкого WebGL слоя: доступную библиотеку и минимальный специализированный путь. Не выбирать библиотеку по привычке. Измерить размер пробной сборки, отрисовать R01 и 14 слоёв R07, записать источники и версии кандидатов. При работе с 3D прочитать docs/knowledge/threejs.md.
- Проверить screenX=originX+(u−v)*a, screenY=originY+(u+v)*b−z*c: старт a=b=80, c=80, слой z=0.16. Почти равные диагонали и видимые боковые грани требуют художественной калибровки; не объявлять пресет классической изометрии точным совпадением.
- Выбрать один WebGL путь и общий контракт render(viewState, viewport), resize, pickStack, dispose. Renderer получает отображаемый снимок и не изменяет модель. 2D renderer использует ту же проекцию и входные данные; физический движок не добавлять.
- Зафиксировать предложенные API будущих модулей: validateLevel/createInitialState; simulateMove; createGameController; solve в Worker; createAnimationPlayer; createStore; createAudio. Описать единицы, владельцев, immutable snapshots, version/generation IDs и границу устойчивого итога и текущей анимации.
- Демонстрационный код изолирован от основной сцены. Результат — ADR с выбранным путём и снимками; полная игровая графика остаётся отдельными задачами. Равноценный выбор разрешён при обновлении зависимых заданий.
