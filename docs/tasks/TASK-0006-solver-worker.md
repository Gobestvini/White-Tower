## 4. Требуемое поведение

- Перебирать допустимые активные стопки через общий simulateMove; канонизировать состояния, исключать повторения. Хранить путь запуска по координатам; пересимулировать найденный путь до isWon, а не доверять одной эвристике.
- API solve(level, state,{requestId, budgetMs}) возвращает solved/unsolvable/timeout/cancelled/error. Только исчерпание пространства доказывает unsolvable; таймаут не объявляет тупик.
- Worker обрабатывает отмену и generation ID, не публикует устаревший ответ после Undo/Restart/load/dispose. Основной поток не выполняет большой поиск и не сериализует лишние кадры.
- Цель штатного ответа 300 мс; максимум для подсказки 2 с. При превышении никакой случайной стрелки. Для валидатора кампании можно использовать отдельный offline бюджет и воспроизводимый отчёт.
- Заложить проверку knownSolution и parMoves. Минимальность parMoves утверждать только после соответствующего полного поиска; кратчайший BFS на малых полях либо честно документированный эквивалент.
